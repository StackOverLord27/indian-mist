## Stock and payment edge cases (owner decisions applied)
Owner decision: `payment.failed` does NOT release a hold (Razorpay lets the customer retry on the same order); it is only logged (`payment attempt failed`, ids and error code, control characters stripped). Release rules unchanged: window closed, or 15 minutes.

1. **Deducted quantity recorded.** Each order line has `deductedQuantity` (units really taken: the hold's quantity, the full quantity when claimed, or only what was left in a shortage; 0 for untracked products). Cancel restocks that number. Orders created before this change have no value and keep the old behaviour (restock the full ordered quantity); documented in the deploy checklist.
2. **No crash windows.** `settleOrderStock` (hold consumed or stock claimed + per-line record + `stockSettled` flag), `releaseReservation` (status + restock) and the cancel route (status + restock) are each ONE Mongo transaction (`inTransaction`; needs a replica set: Atlas, the test container; a standalone local mongod fails). New orders are created with `stockSettled: false`; `repairUnsettledOrders` (called from the existing throttled sweep and from create-order; orders older than 2 minutes, 50 per pass) settles any that were never settled, including "paid, hold already released or missing". `releaseReservation` skips a hold whose order exists. Cancel settles an unsettled order first. The sweep settles/consumes holds of paid orders (new orders via settle, older ones via the old consume).
3. **Unmatched payments.** New collection `UnmatchedPayment` (unique `razorpayOrderId`, payment id, amount when known, source webhook|verify-payment, `seen` counter). Recorded when no pending order and no order exist. If the record cannot be saved the webhook answers 500 so Razorpay retries; otherwise 200 (Razorpay retries only non-2xx, so a 200 ends the retries, and a redelivery just raises `seen`). ## Customer sessions ending unexpectedly and blank customer pages (investigation + fixes)

**Root causes found (code read end to end, then reproduced):**
1. **The customer pages never renewed the session.** Only the admin client (`admin-axios`, `AdminProtectedRoute`) called `/api/auth/refresh`. The access cookie lives 15 minutes; after that the proxy still let `/profile` and `/checkout` load (a refresh cookie existed) but the page's own call to `/api/profile` got 401 and the page sent the customer to sign-in. That is why customers were "signed out at random" (after 15 minutes, after closing the tab and coming back, after a payment), and why the admin was affected much less. Payment verification (`/api/checkout/verify-payment`) had the same gap: a payment that took longer than the access token's remaining life ended in "Payment verification failed".
2. **Blank pages:** `ProfilePageClient` ended with `if (!user) return null` and showed its error banner only when a user existed, so any non-401 failure (429, 5xx, network) was an empty page; checkout prefill treated every failure as "guest" silently.
3. **Rotation could end a healthy session** (hypothesis B, below).

**Hypotheses (each reproduced by a test, on the old code first):**
- A (SameSite=Strict drops cookies on arrival from another site): **REAL.** Chromium test (`e2e/session.e2e.ts`): a link, and a 302 redirect, from another origin to `/profile` or `/checkout` arrive without cookies and land on `/signin` although the session is valid; with the cookies temporarily set to Lax the same four tests land on the page. The Razorpay flow itself is the in-page `handler` (no `callback_url`, no redirect), so a normal payment never leaves the site; the exposure is customers opening the site from an e-mail, another app, a UPI app's return to the browser, or an in-app browser.
- B (lost renewal response, later reuse after the 10 s grace wipes the session): **REAL**, plus a variant: a database error between claiming the token and issuing the new one left the token marked used and the cookie unchanged, so the retry after 10 s wiped the session too.
- C (simultaneous requests each renew): **not a problem for customers on the old code (they never renewed at all)**; the server already handled parallel renewals (audit N1). Now the client renews once for all callers (single flight, also across tabs with Web Locks, plus a "renewed after this request was sent" shortcut).
- D (client clears state or shows blank on a non-401): **REAL** for profile (blank) and checkout prefill (silent). Fixed.

**What changed**
- New `src/lib/customer-session.ts` (`customerApi`, `renewSession`, `classifyFailure`, `failureMessage`) used by profile, profile saves, checkout (promo, create-order, verify-payment, release, prefill) and cart sync. 401 → one shared renewal → retry (and one more after 400 ms); only a 401 that remains means signed out; 429/5xx/network/timeout keep the session and give a retry state; every call has a 20 s deadline, the renewal 10 s.
- Profile page: skeleton, error panel with Retry, redirect to sign-in only on a real sign-out. Checkout: "Loading your saved details…" line and an error notice with Retry (form stays usable); a bag-check notice with Retry on cart and checkout.

A database failure during renewal answers 503 and leaves the cookies alone.

### Skeptical review of the whole auth and session layer (before any redesign)

## Duplicate orders for one payment, and the admin note about them (money code)
**Root cause (confirmed by experiment on a local database, and by the owner's Atlas screenshots):** the live `orders.razorpayOrderId_1` index was PLAIN. Mongoose cannot replace an index of the same name with other options: `Model.init()` rejects with `IndexKeySpecsConflict`, which is only emitted as an `index` event on the model. Nothing in the app listened (`src/lib/db.ts` has no index handling, no code awaits `init()`), so the failure was silent, and `finalizeOrder` relied on the unique index to make the browser confirmation and the webhook exactly-once. With a plain index two documents with the same `razorpayOrderId` are both inserted (reproduced: 5 concurrent calls made 5 orders in the real built app). The unit tests built the index on a fresh database, so they could not see it. (The owner has since made the live index unique and sparse by hand in Atlas; nothing here touched it.)

**Fix, and why this design instead of a Redis lock:** every attempt to create the order for a Razorpay order uses the same `_id`, derived from the Razorpay order id (`src/lib/order-id.ts`, SHA-256, 96 bits). MongoDB's `_id` index always exists and is always unique, so the database itself lets exactly one create in and answers the others with a duplicate-key error; the loser returns the winner's order. It does not depend on any other index, on Redis, on a lock's timeout (a lock that expires mid-work lets two through), or on clocks, so there is no new failure mode and the existing Redis requirement for the pending order is unchanged. Stock: one order means one settlement (`stockSettled` is flipped atomically); for OLDER duplicates already in the database, `settleOrderStock` now takes no stock for an order whose Razorpay order already has a settled twin (two settlements at once collide on the product/hold write and the retry sees the first). Also fixed a race found by the browser test: a late confirmation that read the pending order after the winner had deleted it answered 404 and recorded a false "payment received without an order"; it now looks for the order again first.

**Also:** `ensure:indexes` (`scripts/ensure-indexes.mjs`, report by default; `--apply` needs the typed database name, refuses and lists duplicates, never deletes documents, restores the old index if a build fails; Mongoose's own background index build is switched off in the script so the report is truly read-only); `[db] CRITICAL` log on the first connection per instance, once, plus an admin dashboard warning from a cached `GET /api/admin/health`; the Order model now logs a failed index build; each order records `finalizedVia` and `finalizedAt` (log line `[order] created ... via ... at ...`, small text in the admin order detail, never sent to customers); the admin note says plainly "The same payment was recorded twice ... Ship only ONE" when another order has the same Razorpay payment id (computed when listing, so it also covers the existing pairs; the old "possible duplicate purchase" wording is kept for different payments); layout: the expanded order row sat inside a `whitespace-nowrap` table cell, so long notes, ids and addresses ran past their boxes; now they wrap (checked at desktop, tablet and phone widths).

**Tests:** `tests/duplicate-orders.test.ts` (20: 50 rounds each with a plain index and with no index, 25 with the declared index; browser confirmation + two webhook events + two direct calls at once; with and without a stock hold; legacy duplicate pairs settled 20 times at once; the late-confirmation race; the notes), `tests/ensure-indexes.test.ts` (11, real child process against a local database with the conflicting index, with and without duplicates), `tests/db-health.test.ts` (10), `e2e/duplicate-orders.e2e.ts` (6; the real app, a plain index, 12 rounds of confirmation + webhooks at once; the note wording and layout at 3 widths; the dashboard warning). ## Date and time inputs in the admin (promo expiry) and the shop's time zone
**Bug, reproduced** (`tests/shop-time.test.ts` runs the old code lines under `TZ=Asia/Kolkata`; `e2e/promo-expiry.e2e.ts` reproduced it in a real browser with the old code: picking 21:45 showed 16:15): the pricing page saved the picked time correctly (`new Date("2026-11-15T18:03").toISOString()` parses the typed text in the browser's zone) but showed it back with `new Date(iso).toISOString().slice(0, 16)`, the UTC clock parts, so in India time the field read 12:33 PM right after picking 6:03 PM. The stored instant was right; the display was shifted by 5 h 30 min (and after a reload it stayed shifted). In a UTC browser the two cancel out, which is why it looked fine to developers.
**Every conversion between an input and a stored date:** only one existed, the promo expiry on the pricing page. There is no date input for blog posts (the publish date is set by the server when a post is published) or anywhere else in the admin.
**Decision: the shop's time zone is always India time (IST, Asia/Kolkata, UTC+05:30, no daylight saving), with an "IST" label,** not the browser's zone. Reasons: a promo that "ends at 11:59 PM on 15 November" is a business time, not a point on the admin's laptop clock (a laptop abroad or behind a VPN would show and edit a different time for the same saved promo); the shop sells in India; and a single fixed zone also fixes server-rendered dates (below). `src/lib/shop-time.ts` is the one place: `toShopInputValue` / `fromShopInputValue` (input text <-> UTC instant, built from the typed parts, never `new Date("local string")`), `formatShopDate` (display) and `hasExpired`. Stored values are UTC instants as before; nothing in the database changes, and existing promos keep their instants (they now simply read correctly).
**Server side:** `POST /api/checkout/promo` and `create-order` now use `hasExpired(expiresAt)`: the exact instant, no rounding to a minute, hour or day. **"Expires at 6:03 PM" means the code stops working at 6:03:00.000 PM India time** (usable up to 6:02:59.999; before this change the exact millisecond itself was still valid, `<` instead of `<=`). A code with no expiry never expires. An expiry that passes while the checkout page is open is refused when the shopper presses Pay (nothing is held); a payment already started keeps the price it was started at. The admin page's "expired" badge and the active/inactive split use the same function.
**Field:** label "Expires At (IST)", hint "India time (IST). The code stops working at exactly this minute. Leave blank for no expiry." and a "Clear" button (the browser's own clear also works); empty means no expiry and is saved as `null`.
**Dates rendered for customers (item 5):** the blog list and the blog page (server-rendered on Vercel, which runs in UTC) formatted dates in the server's zone, so a post published between 00:00 and 05:30 India time showed the PREVIOUS day, and the browser then re-rendered a different text (a hydration mismatch). Now India time on server and browser. Order dates (My Orders, admin orders, the dashboard's unmatched payments, "order created by ...") use the same formatter; admin times carry "IST". There is **no estimated delivery date** in the shop (`ShippingForm` has it commented out), so nothing to fix there; e-mails print only the year.

- **Rate limiter `analytics: false`** for all three limiters. `autoIndex` untouched.
- **Order `_id`** = first 24 hex characters (96 bits) of `SHA-256("indian-mist:order:" + razorpayOrderId)`, a hash, not padding (`src/lib/order-id.ts`). The order number is the last 6 hex characters of that id, i.e. 24 bits taken from a hash, so they are uniformly spread (chi-square test over 50,000 ids, `tests/order-id-derivation.test.ts`). Two orders sharing a **number** is the birthday problem over 16.7 M values: about 50 % at roughly 4,800 orders, about 0.003 % at 100 orders. The number is only a label; the full 24-character id is what the database uses, and two different Razorpay orders colliding on it is not realistic (96 bits). Orders created before the change keep their time-based ids and numbers; nothing rewrites them.
